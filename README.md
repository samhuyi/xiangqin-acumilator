# 《相亲模拟器》微信小游戏

一款以中国相亲现实为背景的**文字 Roguelike**。玩家设定出身与人生目标，以「天」为单位推进，在存款、好感度、健康、事业、颜值、家境、情绪七项指标之间取舍，走完一条完整的相亲之路。

本工程由参考项目《相亲模拟器》（HTML 版）迁移而来，**玩法完全一致**，并按要求把全部游戏数据接入数据库。

## 核心特性

- **玩法与参考项目一致**：状态机、关系推进、胜负判定、各行动的数值公式均与参考项目等价（`tools/smoke.js` 已端到端验证）。**两处有意差异**：① 事件数值的 ±25% 随机浮动已按需求移除，改为确定性结算；② 相亲对象从「随机拼装」改为数据库里的固定花名册。
- **数据与逻辑分离**：事件、角色、难度、渠道、约会档位、交往风格、结局、数值常量、旁白文案全部来自数据库，`js/core/engine.js` 不含任何游戏数据。
- **云数据库为唯一数据源**：微信云开发数据库 → 加载即缓存、二次秒开；云端数据不完整 / 读取失败时，游戏显示错误页并列出问题清单，方便定位云端数据问题。
- **美术资源集中管理**：图片统一放 `assets/images/`，`manifest.js` 按「逻辑 key → 路径」自动登记（分 `main` 启动即下 / `lazy` 按需下 / `packs` 分包三组），`role-map.js` 负责把游戏数据接到图上；职业头像与场景图走独立分包、行动页 / 结局页的页头背景走按需下载，都不跟首屏抢带宽。
- **操作页只有两个方向入口**：主界面「今天想做什么？」只留 **寻找相亲机会** 与 **其余安排** 两个按钮，单击即进各自的二级页（页头是背景图 `seek_bg_<性别>` / `upgrade_bg_<性别>`），具体安排在二级页里挑。二级页是「聚焦页」——不重复铺状态条、长期目标与近期经历；页面标题与副标题全部取自 `texts`（有对象时「寻找相亲机会」自动变成「和 TA 的事」）。
- **两级页面 + 明确反馈**：选择相亲 / 随机事件后进入全屏二级页（隐藏属性与目标，页面更聚焦），事件内先选中选项、再点「确认」提交；**确认后不跳页——结果直接展示在原选项区域，场景背景与双方头像继续保留**，点底部「继续」才推进时间。属于「行动」类的结果（相亲机会 / 休息 / 加班）仍走独立结算页，给出结果图标、花费、正文与属性增减标签；回到主界面后**属性条会动**：条长在 0.9 秒内从结算前平滑滑到结算后，变化的那一段单独上色（涨用涨色直接盖在条上、跌用跌色画在填充底下随动画淡出），数值同步滚动变色，条上方还会飘出本次涨跌。
- **倒计时只在「真的还空窗」时走表**：相亲期限用「连续单身天数」计数，以下几种情况都**暂停**——当天已经相到人（`lead` 存在）但还没赴约初遇、初遇中、接触中；**只有「单身且手上没人」才扣减**，确定关系后归零。因此「刚相到人、还没见面」这段时间没有期限压力，期限到点也不会在接触中判负，可以把这段关系走完。
- **事件与聊天按接触阶段分级**：暧昧向内容（接触中即可）与婚嫁向内容（见家长 / 要孩子 / 婚后同住，需告白成功）分开。事件用一个可选的 `stage` 字段声明「最低接触阶段」，聊天用 `phases` 显式列出可出现阶段（多出一个 `lead` —— 见面前也能在微信上先聊），顺序取自常量 `RELATION_ORDER`。
- **好感度是动态值**：上限随关系阶段变化——单身 / 初遇 / 接触中是 **100**，告白成功（恋爱 / 已婚）放大到 **500**。告白成功那一刻旧刻度按 `CONFESS_AFF_RESCALE` 换算到新刻度，**求婚成功率也按新刻度算**（`PROPOSE_AFF_BASE` / `PROPOSE_AFF_DIV`）：刚在一起时几乎不可能成功，必须继续约会、继续聊，把感情养上去才有把握；没到 `PROPOSE_AFF_MIN` 时行动菜单会直接写「还差多少」。约会 / 事件给的好感在恋爱后同步放大（`DATING_AFF_GAIN_AMP`），扣分则按刻度倍数等比放大，保持惩罚的相对分量。三档难度实测进入恋爱后能养到的好感峰值约为 简单 490 / 普通 430 / 困难 345。
- **主界面即入口**：点右上角对方头像（还没有对象时是「?」）进「对方资料」页，看 TA 的年龄 / 职业 / 性格 / 人格 / 家庭 / 外形 / 爱好 / 认识方式 / 颜值 / 家境；点左上角**自己的头像**进「近期变化」页（关键事件 + 每项属性「从 x 变为 y」，头像是唯一的入口，属性条本身不可点）；点日志块进「近期经历」页（每条记录都写明事件 / 你的选择 / 结果）。**属性区固定为三行 × 每行两条**：存款 / 健康、事业 / 颜值、家境 / 情绪（顺序就是 `stat_defs` 的数组顺序）。**好感度不占格子**，直接挂在对象头像正下方，显示成「当前 / 上限」（如 `218/500`）——**聊天框里只要有人就出现**（已确定关系，或已相到人、还没赴约都算），不用点进去才看得到。
- **相亲机会结果页 = 信封卡片**：有相亲机会时，结果页先给「花销」框，再画一张信封样式的对象信息卡（带信封翻盖 + 头像），姓名 / 职业 / 性格 / 家庭 / 条件**逐项独立背景框**。所有文字与头像均来自数据库。
- **头像从数据库读**：出身背景头像在 `backgrounds.avatar`、对象职业头像在 `materials.jobs[].avatar`；`assets/images/role-map.js` 只在数据库缺该字段时兜底，避免旧数据白屏。**缺某个性别的图会打 `console.warn` 并回退到反性别图**，不再静默用错头像。
- **微信闲聊**：**已相到人就能聊**——包括「还没赴约、只加了微信」的阶段（此时抽的是带 `lead` 标签的对话，口吻是「还没见过面」），以及暧昧 / 恋爱 / 婚后。入口在**「寻找相亲机会」二级页**里（不再散落在主界面），进入微信对话框样式的二级页——对方先发几条消息，从选项里挑一条回答。**不同回答与事件选项走同一套结算规则：对多项属性同时产生增减（有增有减、奖惩加倍）**，不只是好感度与情绪。结算完点「结束闲聊 · 进入下一天」即推进时间回主界面。剧情分四类主题：日常闲聊、**灵魂拷问**（按对象人格出题，踩雷一记掉 20 点以上好感）、**暧昧事件**（同样按人格出题，接住了能一次涨 15 点以上）、以及**现实议题**（父母催婚、个人慢热、通勤加班、房子首付、家里老人）。**见面前聊出来的好感会在初遇时折算成印象分**（上限 `LEAD_CHAT_AFF_MAX`），见面开场白会点明这件事。另外，**对方会主动找你**：在一起之后每天开头有 30% 概率对方主动发来微信，聊完这一天就过去了（**跳过当天的行动选择**）；**微信上一共聊过 `CHAT_MUST_DATE_AFTER`（默认 2）次**（玩家自己点开的和对方主动发来的都算）后会触发固定剧情「必须出门约会」，聊完进入**禁止再聊**的状态——此时微信入口还在，但点进去只会看到「我们还是多当面接触吧」，必须先安排一次约会才会解锁（约会完成后计数清零）。见面前（`lead`）对方不会主动发消息，免得把「赴约」这件事顶掉。**只要微信里有人，入口就一定在**：题库为空（云端 `chats` 还是旧数据）时点进去是一页说明 + 「返回」，而不是让入口凭空消失。

- **相亲对象全部来自数据库**：24 位对象（12 男 12 女）一人一条登记在 `partners` 集合里——姓名、性别、年龄、职业、**头像**、外形、性格、家庭、爱好、认识方式、人格、颜值、家境、眼缘、简介。引擎只负责「按性别筛 + 加权抽 + 补水」，**不再随机拼装**姓名 / 职业 / 数值；同一局优先抽没遇见过的人。
- **相亲图鉴**：主界面底部「相亲图鉴」（标题页也有入口）→ 分「女生 / 男生」两栏，一人一张卡。已解锁显示**头像 + 姓名 + 达成的进展**（已遇见 / 初次见面 / 接触中 / 恋爱中 / 已结婚 + 好感度峰值），未解锁显示**黑框 + ？**。点已解锁的卡片进资料页看完整设定。收集进度**跨局累计**（本地存档 `xq_gallery_v1`），对象资料始终来自云端。
- **数值结算不随机浮动**：事件选项写多少就结算多少（乘上难度 / 风格 / 对象等固定系数），因此「结算里显示的变化」与主界面上看到的数值完全对得上。见面第一印象的随机项也已移除，改为每位对象自己的「眼缘」`first`。补齐属性覆盖的附带数值也由 `id` 确定性生成，不是运行时随机。
- **结局页可看广告领奖励**：结局页底部两个入口**并行**——「看广告 · +5000」与「直接再开一局」，玩家自己选（广告不是继续游戏的强制门槛）。广告看完的奖励在**下一局开局**发放，不回改这一局结局页上已经展示的成绩；中途退出 / 拉不起来都不发奖、也不卡人。广告位 ID、奖励数值、总开关、全部文案都在云端（`constants` + `texts`），没配广告位时自动降级成只显示「直接再开一局」。
- **告白 / 求婚结算页带头像与背景**：这两件事是关系里的关键节点，结算页顶部会画出当时的场景背景与「我 / 对方」两张头像（场景先按结算正文关键词匹配，匹配不到再退 `role-map.js` 的 `actionScene` 默认值）。要展示头部的行动由常量 `RESULT_HEAD_ACTIONS` 配置（默认 `confess,propose`）。
- **交互一致性**：非选项类按钮（开始游戏 / 玩法说明 / 重开等）单击即执行；选项类按钮单击选中、由底部「确认」统一提交。所有选项按钮共用同一套视觉，不靠颜色区分主次。**设定页四步（性别 / 出身 / 目标 / 难度）同为单选**：点一次选中、再点一次取消、点「确认」才推进，回退上一步不会残留高亮。
- **标题页聚焦**：按钮区从画布垂直 50% 处开始，下方不铺白色蒙层，画面干净、按钮整体靠下。

## 快速开始

1. 用微信开发者工具「小游戏」项目打开本目录（需正式 AppID）。
2. 接入数据库：见下方「数据库接入」（⚠️ 云开发需正式 AppID，测试号/游客号不支持）。
3. 编译运行后，若控制台显示 `数据源：network` 即表示已读到云数据；若显示错误页，按页面列出的问题清单到云控制台排查。

## 数据库接入

游戏数据由 15 个集合组成：`events / backgrounds / goals / difficulties / channels / date_types / court_styles / style_events / chats / partners / personalities / endings / constants / materials / texts`（共 553 条文档）。

**方式一：微信云开发（唯一数据源）** —— 完整分步见 [`docs/云开发接入.md`](docs/云开发接入.md)

```bash
node db/import.js          # 生成 db/export/import/*.json
```

要点：云控制台建 15 个同名集合 → 逐个导入 `.json`（JSON Lines，首次导入选 Insert）→ **集合权限设为「所有用户可读」** → 在 `game.js` 填入环境 ID：

```js
var CLOUD_ENV_ID = '你的云环境ID';   // 留空 '' 则用默认环境
```

**数据更新**：修改数据后重跑 `node db/import.js` 生成新文件，云控制台重新导入时冲突处理改选 **Upsert / 覆盖**——用 Insert 会跳过已存在的 `_id`，改了也不生效。

## 美术资源与分包

职业头像放 `assets/images/role/`，命名 `职业-性别.png`（性别用 `m` / `f`），如 `programmer-m.png`；场景背景放 `assets/images/scene/`，命名 `bg-场景名.jpg`，如 `bg-cafe.jpg`。

二级页头部背景图分两处，命名里都带性别后缀：

| 用途 | 路径 | 说明 |
| --- | --- | --- |
| 「寻找相亲机会」页头 | `assets/images/seek_bg_<性别>.jpg` | 按**主角**性别取图 |
| 「其余安排」页头 | `assets/images/upgrade_bg_<性别>.jpg` | 按**主角**性别取图 |
| 结局页页头 | `assets/images/end/end_<结局类型>_<性别>.jpg` | `结局类型` 取 `happymarry` / `badmarry` / `alone` |

> 结局用哪张图**不是代码里写死的**：每个结局记录带一个 `art` 字段（见 `endings` 集合），渲染层只负责拼 `end_<art>_<性别>`。想给某个结局换画面，改数据即可。

> ⚠️ **图片文件名必须是 ASCII**（英文 / 数字 / `-` `_`），不要用中文。
> 中文文件名在打包与真机取图时可能因编码不一致而加载失败，表现为「图片全都不显示」。
> `tools/gen-art-manifest.js` 会直接拦下中文文件名并报错退出。

两张映射表把游戏数据接到图上：

- `assets/images/role-map.js`：`background`（出身背景 → 职业 key）、`job`（对象职业 → 职业 key）、`eventScene` / `dateTypeScene` / `sceneKeys` / `meetScene`（事件 → 场景 key）。
- `assets/images/manifest.js`：由脚本自动生成，记录 `main`（启动即下）/ `lazy`（按需下）/ `packs`（分包）三组资源，**不要手改**。

图片改动后的完整流程（两步都是幂等的，可以反复跑）：

```bash
python tools/compress-assets.py    # 压缩：头像 360px PNG、场景/主包/结局图 750px JPEG
node tools/gen-art-manifest.js     # 重新生成 manifest.js（含中文文件名检查）
```

> `compress-assets.py` 会把 PNG 转成 JPG（体积约为原来的 1/5），所以**渲染层不要手拼 `.png` 后缀**，一律通过 `art.js` 取图（`art.pageBg` / `art.endBg` / `art.roleImg` / `art.sceneImg` 等），路径由 manifest 决定。

### 加载机制

图片分三档优先级。`art_role` / `art_scene` 是 `game.json` 声明的两个分包，分包根目录必须各有一个 `game.js` 空入口。启动时 `js/ui/art.js` 会：

1. **显式加载主包图**（`intro_bg`）——它不在任何分包里，必须单独加载；
2. 对每个分包**先调 `wx.loadSubpackage`，等回调到了才排这个分包的图**；
3. 分包就绪（或下载失败）后整体「解冻」一次：清掉失败标记与重试计数再重新排队；
4. 单张图失败最多重试 2 次；每张图就绪都会触发重绘，所以图片是「陆续出现」的，不会一直空着；
5. 上面全部排完之后，再后台补下 `lazy` 那批（行动页 / 结局页的头部背景，共 10 张约 660KB）——**它们不跟关键图抢带宽**，图没到位时页头先画纯色，图到了自动补上。

> **为什么必须等分包回调**（真机「除了主界面图全都加载失败」的元凶）：
> 早期版本在 `loadSubpackage` 之前就把分包里的图排上队了。开发者工具里分包是本地文件，`wx.createImage` 立刻命中，看不出问题；真机上分包还没下完，提前排的图必然 `onerror`，重试两次（约 1.5 秒）后就被标成 `FAILED`，而真机下载往往不止 1.5 秒 —— 等分包终于下完再排队时，会被 `enqueue` 的 `FAILED` 判断直接挡掉，图就永久没了。现在的做法是：分包 `loading` 期间失败的图**不消耗重试次数、不标 FAILED**，只记进待处理集合，分包回调一到统一重新排队。`art-smoke.js` 里有一条专门的回归（`subpackageDelay` 模拟慢分包），把这条路径锁死。

全部落定后控制台会打一条汇总：`美术资源：32/32 张就绪（主包 intro_bg=ok，分包 art_role=ready art_scene=ready；按需 0/10）`。
`按需 x/10` 只反映那批页头背景下载了几张，不影响 `total` 的判定（否则汇总行永远打不出来）。
如果标题页顶部出现一行小字（`美术资源加载中…` 或 `美术资源异常：N 张加载失败`），说明资源没齐，控制台会有具体的失败路径。

**事件与场景一一对应**（四级匹配，前面的优先）：事件若在 `role-map.js` 的 `eventScene` 里显式指定场景（值写 `null` 可强制不展示背景）以它为准；否则按约会档位（`dateTypeScene`）取默认场景；再否则按事件文案 + 选项 + 初遇旁白关键词兜底匹配（`sceneKeys`）；最后，若本次是「赴约初遇」（`action=meet`，它没有档位概念），落到默认的 `meetScene`。四级都匹配不到才不展示背景（兜底为纯色头部）。

### 图片不显示怎么排查

按顺序看这三处，基本能定位到具体哪一层：

1. **控制台汇总行** `美术资源：x/y 张就绪`。`x < y` 说明有图没进来，同一行会给出分包状态和失败路径。
2. **标题页顶部的小字**。正常情况不出现；出现 `美术资源加载中…` 说明还在下载，出现 `美术资源异常：N 张加载失败` 说明确实缺图。
3. **文件名是否 ASCII**。跑一次 `node tools/gen-art-manifest.js`，有中文文件名会直接报错。

如果分包始终下载不下来，可以让图片走主包（当前主包约 1.2MB，两个分包合计约 3.0MB，总额远低于小游戏 4MB 主包 / 30MB 总包上限）：

1. 删掉 `game.json` 里的 `subpackages` 字段（保留 `role/game.js`、`scene/game.js` 不影响）；
2. `node tools/gen-art-manifest.js` 重新生成注册表；
3. 代码不用改——`art.js` 对「分包不存在 / 下载失败」都有按路径直取的兜底。

代价是首次启动要多下载约 3.0MB。

## 行动流程（两级菜单）

主界面的「操作页」只有**两个方向入口**，单击即进（导航按钮不做二次确认）：

```
操作页（phase='choose'）
├─ 寻找相亲机会 → 二级页 phase='seek'，页头背景 seek_bg_<性别>
│    · 还没相到人      → 选渠道（托人介绍 / 婚恋 App / 红娘 …）
│    · 相到了没见面    → 赴约初遇 · 见 TA ／ 微信闲聊
│    · 接触中 / 恋爱中 → 约会 ／ 告白（恋爱后是求婚）／ 微信闲聊 ／ 分手
│    · 婚后            → 约会 ／ 微信闲聊 ／ 准备要个孩子
└─ 其余安排     → 二级页 phase='upgrade'，页头背景 upgrade_bg_<性别>
     · 过日子 ／ 提升自己 ／ 加班挣钱 ／ 休息一天
```

两个二级页都是「聚焦页」：**只画页头背景图 + 这一类的操作 + 底部「返回 / 确认」**，不再重复铺状态条、长期目标与近期经历（这些留在操作页）。页面标题与副标题分别取 `texts.play` 的 `seekPageTitle` / `seekPageSub` 与 `upgradePageTitle` / `upgradePageSub`；已经有对象时「寻找相亲机会」的标题换成 `seekPageTitlePartner`（`和{name}的事`）配 `seekPageSubPartner`。

二级页里的具体安排仍然是**列表项：点一次选中、再点一次取消、点底部「确认」才提交**。返回键（`backToChoose`）回到操作页。

## 二级页一览

各个二级页都从**主界面 / 标题页**进入，返回键回到主界面（`PREV_SCENE` 记来源场景）。所有文案都在 `texts` 集合里，渲染层不硬编码。

**对方资料（`scene='partner'`，点右上角头像）** —— 有对象 / 有待见面对象时展示 TA 的完整设定：年龄、职业（含职业说明）、性格、人格、家庭、外形、爱好、认识方式、颜值、家境；已经确定关系时额外显示当前好感度，还是「待见面」状态时给出「可以去赴约初遇」的提示。还没有对象时点头像（画面上是「?」）也能进，页面给一句引导文案，而不是无处可点。文案在 `texts.profile`。

**近期变化（`scene='stats'`，点左上角主角头像）** —— 依次展示：

1. **当前状态**：七项属性一次摆齐（好感度在这里仍然保留，方便总览）；
2. **本次结算**：刚结束那一天的全部涨跌（还没结算过则不显示）；
3. **按天回看**：最近若干天的每日涨跌，最新在前。每天先给**关键事件**标题，再逐项列「{属性}：从 {旧值} 变为 {新值}」，附带动标签；
4. **近期合计**：这段时间的净变化。

每日涨跌在结算时写入 `S.history`（只记非零项，避免噪音；同时记录结算前后的快照与关键事件标题），长度由常量 `STAT_HISTORY_MAX` 限制。文案在 `texts.statlog`。

**近期经历（`scene='recent'`，点日志块）** —— 按天回看最近若干次行动，每条卡片分三段：**事件**（标题 + 摘要）、**你的选择**（所选选项名）、**结果**（结算文案），左侧一条按结果类型着色的竖条。记录来自 `S.acts`，长度由常量 `ACTLOG_MAX` 限制。文案在 `texts.recent`。

**微信闲聊（`scene='chat'`，「寻找相亲机会」二级页里的「微信闲聊」按钮）** —— **只要聊天框里有人就出现**：已相到人、还没赴约（`lead`，题目是「还没见过面」的口吻），或暧昧 / 恋爱 / 婚后。进页后对方先发几条消息（`texts.chat` 提供页头文案，开场白来自 `chats` 集合），底部一排候选回答；选中一条再点「发送」提交，随后对方回一条。**不同回答只影响好感度与情绪**，其余指标不动；结算后点「结束闲聊 · 进入下一天」推进时间（`ACTION_DAYS.chat`）。文案在 `texts.chat`。

> **入口不会因为数据缺失而消失**：以前题库为空时入口会被整块藏掉，玩家看起来就像「功能没了」。现在只要微信里有人就给入口；万一 `chats` 里真的没有这个阶段的题目（通常是云端数据没重导），点进去是一页 `emptyLine` / `emptyHint` 的说明 + 「返回」，同时控制台会打一条明确的告警，指名要重新导入 `db/export/import/chats.json`。

三种进入方式与两种特殊剧情：

- **手动进入**：点主界面「微信闲聊」，选一条答完即走，可以中途「返回」。
- **对方主动发来**：已经在一起（有对象）时每天开头判定一次（`PARTNER_CHAT_RATE`，默认 30%）；还没见面的 `lead` 阶段不触发。命中后聊天页顶部标出「对方主动发来了消息」，**没有「返回」**；聊完这一天就算过完，直接进下一天——即**跳过当天的行动选择**。
- **必须出门约会**：主动聊天**累计超过 `PARTNER_CHAT_MUST_DATE_AFTER`（默认 2）次**后，下一段聊天不再随机抽题，而是固定的 `CHAT_MUST_DATE_ID`（默认 `c_mustdate`）剧情。聊完进入 `S.mustDate` 状态：**微信入口还在，但点进去只显示一句「我们还是多当面接触吧」**，也不再有主动聊天——必须先安排一次约会（`goDate`）才能解锁，约会完成同时把主动计数清零。
- **灵魂拷问（`kind: 'grill'`）**：按对象人格（`personalityId`）投放，标题区标出「灵魂拷问」。选项里有一条 `correct`，踩雷的选项一次掉 20 点以上好感，答完会给出「这话说得不太妙 / 答到点子上了」的判定。
- **暧昧事件（`kind: 'flirt'`）**：同样按人格投放，标题区标出「暧昧时刻」。答对一次涨 15 点以上好感，是升温最快的一条路；答不对也不至于翻脸，但机会就浪费了。

**相亲图鉴（`scene='gallery'`，主界面底部「相亲图鉴」/ 标题页入口）** —— 分「女生 / 男生」两栏（默认展示异性），一行三张卡片：

- **已解锁**：圆形头像 + 姓名 + 达成进展（`已遇见 / 初次见面 / 接触中 / 恋爱中 / 已结婚`）+ 好感度峰值；点卡片进 `scene='galleryDetail'` 看完整资料（年龄 / 职业 / 性格 / 人格 / 家庭 / 外形 / 爱好 / 认识方式 / 颜值 / 家境 + 首次遇见天数 / 最近见面天数 / 是否已有孩子）。
- **未解锁**：黑框 + `？` + `？？？` + 「未解锁」。

卡片上的**资料来自云端 `partners`**，解锁与进展来自**本地存档 `xq_gallery_v1`**（跨局累计，每次存档自动同步）。文案在 `texts.gallery`，阶段顺序在 `constants.GALLERY_ORDER`。详见 [`docs/数据库设计.md`](docs/数据库设计.md) 第 5 节。

| `RESULT_HEAD_ACTIONS` | `confess,propose` | 结算页要展示「场景背景 + 双人头像」的行动（逗号分隔；这类行动没有事件对象） |

| `GALLERY_ORDER` | `met,meeting,talking,dating,married` | 图鉴里「达成的进展」的阶段顺序（只升不降） |
| `AFFECTION_CAP_BASE` | 100 | 好感度在单身 / 初遇 / 接触中的上限 |

排版类尺寸（页头高度、按钮高度、各页边距）是**代码常量**，在 `js/ui/render.js` 顶部集中声明、不散落各处：`PAGE_HEAD_H`（行动二级页页头 156）、`END_HEAD_H`（结局页页头 172）、`PAD`、`LINEH`、`CARD_PAD`、`BOTTOM_GAP`、`BAR_BTN_H`、`BAR_RESERVE`。

主界面上的操作提示在 `texts` 的 `play` 文档（`profileTap`「点头像看资料」贴在对象头像下 / `statTap`「点头像看属性变化」贴在主角头像下 / `recentTap` / `logTap`，留空则不显示）。

**属性条的展示位也是数据驱动的**：`texts.stat_defs` 是一个数组，**数组顺序就是主界面的排版顺序**（渲染层一行放两条，所以默认排成「存款/健康 · 事业/颜值 · 家境/情绪」三行）。每项属性还可带 `slot` 字段：带 `slot` 的项不占网格格子，而是挪到指定位置 —— 目前只有 `affection`（好感度）带 `slot: 'partnerHeader'`，意为「挂在对象头像正下方，显示成『当前 / 上限』」。它的 `max: 100` 只是单身期的刻度，渲染时按 `engine.affectionCap(S)` 取当前上限（恋爱后自动变 500）。

想调整排版：改 `tools/gen-seed.js` 里 `stat_defs` 的数组顺序即可。想恢复成「好感度和其它属性排在一起」，把 `slot` 字段删掉、重跑 `node tools/gen-seed.js`，代码不用改。

## 页面动效与交互约定

这几条是全局约定，改界面时保持一致性：

- **首页按钮（标题页的「开始游戏 / 玩法说明 / 相亲图鉴 / 继续游戏」）**：文字**水平居中**、字号比通用按钮**大一号**（17 vs 16）、底色**70% 不透明**，并且**左右边缘渐隐到全透明**（`paintSoftPanel()`：横向 `0 → alpha → 0` 的渐变 + 纵向两端收紧），所以按钮没有硬边框，像浮在背景上。实现是 `titleButton(label, sub, onClick, opts)`。
- **页面过渡动效**：换页时不逐个登记，而是靠**页面指纹**（`pageKey()` = 场景 + 阶段 + 是否开着叠层）自动检测。指纹一变就播一次 `TRANS_MS = 260ms` 的淡入 + 上移 20px（`easeOutCubic`），内容层与固定层（页头 / 叠层 / 底部操作区）一起位移淡入。同一页重复绘制指纹不变，不会一直重播。测试里用 `render._transOn(false)` 关掉，避免排版断言受位移影响。
- **提示条（飘字）**：走**带存活时间的队列** `flashQueue`（`FLASH_MS = 3200ms`），画在**固定顶层**（底部操作区之上），因此不会被「每帧重绘 + 属性条动画」挤掉。`consumeFlashes()` 只入队、`drawFlashes()` 按 TTL 过滤。**这就是「每 30 天结算收支」提示以前看不见的根因**：旧实现画一帧就立刻清空 `S.paydayFlash`，而主界面每帧都在重绘，提示存在时间不足 1 帧。
- **列表选项**：一律「点一次选中、再点一次取消、点底部确认才提交」；**导航类按钮**（进二级页 / 返回 / 继续）单击即执行。
- **操作按钮尽量靠下**：标题页按钮区从画布垂直 50% 处开始，下方不铺白色蒙层。



进结局时顶部是一张**结局插画**（固定在屏幕顶部，不随内容滚动），下面是原来那套内容（结局标题 → 双人头像 → 结局正文 → 「为什么」原因框 → 数值一览 → 底部「再开一局 / 回到标题」）。

插画路径 `assets/images/end/end_<art>_<性别>.jpg`，其中 `<art>` 来自结局记录的 **`art` 字段**，13 个结局只对应 3 种画面：

| `art` | 画面 | 命中的结局 |
| --- | --- | --- |
| `happymarry` | 修成正果 | `marry`（尘埃落定）、`true_love`（满分答案） |
| `badmarry` | 被逼婚 | `forced`（在父母的催促下匆忙相亲结婚） |
| `alone` | 一个人 | 其余 10 个（独自富有 / 山顶的风 / 落地生根 / 自由人生 / 破产 / 身体亮红灯 / 事业崩塌 / 撑不住了 / 停在原地 / 时间到了） |

## 微信闲聊数据（`chats` 集合）

闲聊场景完全数据驱动，默认 36 条，按 `kind` 分成四类：

| `kind` | 条数 | 说明 |
| --- | --- | --- |
| `normal` | 23 | 日常闲聊（`c_*` 八条基础 + 见面前的 `l_*` 四条 + 父母催婚 `c_parents_*` + 个人慢热 `c_slow_*` + 现实因素 `c_real_*`） |
| `grill` | 6 | **灵魂拷问**：按人格投放，踩雷大幅掉好感 |
| `flirt` | 6 | **暧昧事件**：按人格投放，答对大幅涨好感 |
| `mustdate` | 1 | 「必须出门约会」的固定剧情（`c_mustdate`），不进随机池，由常量点名调用 |

每条结构：

```json
{ "_id": "g_money", "kind": "grill", "personalityId": "money",
  "phases": ["talking","dating","married"], "minAffection": 10, "weight": 6,
  "opener": ["问你个正事", "要是结婚了，首付你家能出多少？"],
  "options": [
    { "label": "首付我来想办法，不用你操心", "reply": "……这话我爱听。", "affection": 11, "mood": 3, "correct": true },
    { "label": "你家不也有吗", "reply": "哦。我知道了。", "affection": -27, "mood": -8 } ] }
```

抽题规则在 `engine.pickChat(s)`，按顺序过滤：

1. 当前**聊天阶段**必须出现在 `phases` 里 —— 阶段由 `engine.chatStage(s)` 给出：有对象时就是关系阶段（`talking` / `dating` / `married`），**只有 `lead`（已相到人、还没赴约）时算作 `lead`**。所以「见面前」的题目靠 `phases: ["lead"]` 单独投放，不会串到别的阶段；
2. 好感度不低于 `max(minAffection, CHAT_MIN_AFFECTION)`；
3. **`personalityId` 不为空时必须与对象人格一致**（灵魂拷问 / 暧昧事件就靠这一条做到「按性格出题」）；
4. 固定剧情（`CHAT_MUST_DATE_ID`）**不进随机池** —— 只有主动聊天攒够次数时才由 `pickChat` 直接点名返回；
5. 剩下的按 `weight` 加权随机。

`applyChat(s, opt)` 与事件选项走**同一套结算口径**：都过 `applyFx`，对全部 7 项属性生效，且每个选项都「有增有减」（规则与放大系数见 [事件与聊天的结算规则](#事件与聊天的结算规则)），返回 `{delta, reply}`；好感度夹在 `0 ~ engine.affectionCap(s)`（单身 / 接触中 100，恋爱后 500）。选项上的 `correct` 只用于展示「答对 / 答错」与数据校验，**不参与结算**（增减仍由 `fx` 决定，不走两套逻辑）。

| 想改什么 | 改哪个集合 | 备注 |
| --- | --- | --- |
| 闲聊场景 / 开场白 / 候选回答 / 效果 | `chats` | `fx` 为各属性增量；`kind` 决定归类，`personalityId` 决定投放对象 |
| 新增一条灵魂拷问 / 暧昧事件 | `chats` | 记得给 6 种人格各配一条（`smoke.js` 会校验人格覆盖率，缺了直接报错） |
| 闲聊是否出现 / 耗时 / 主动概率 | `constants` | `CHAT_MIN_AFFECTION`、`CHAT_DAYS`、`ACTION_DAYS.chat`、`PARTNER_CHAT_RATE` |
| 见面前也能聊 / 印象分折算 | `chats` + `constants` | 对话标 `phases: ["lead"]`；上限与阶段标签用 `CHAT_LEAD_PHASE` / `LEAD_CHAT_AFF_MAX` |
| 「必须出门约会」的阈值与剧情 | `constants` + `chats` | `CHAT_MUST_DATE_AFTER` 调阈值（`S.chatCount` 统一计数）；**所有 `kind: "mustdate"` 的条目都进固定剧情池**，按 `weight` 抽一条 |
| 闲聊页文案 | `texts` | `chat` 文档（标题 / 返回 / 发送 / 我 / 空态 / 涨跌 / 回复） |

## 接触阶段分级（暧昧 vs 婚嫁）

同一份内容在不同关系阶段该不该出现，靠**接触阶段**判断。顺序由 `constants.RELATION_ORDER` 给出（`single < meeting < talking < dating < married`），逻辑层只做比较、不写死阶段名。

**事件（`events.stage`，可选）** —— 声明「最低接触阶段」。不写 = 不限阶段，按 `phase` 走原来的关系匹配；写了就必须走到该阶段才可能抽到：

- 约会事件里 `dt_question_kid`（要不要孩子）、`dt_question_live`（婚后和父母同住）标 `stage = "dating"`，**接触中不会抽到，告白成功后才出现**。
- 抽取在 `engine.stageOk(s, ev)` 里统一判断，`pickEvent` / `goDate` / `pickMeetingEvent` 都会过滤。

**聊天（`chats.phases`）** —— 显式列出允许出现的阶段。见家长这种明确的婚嫁信号只给 `["dating","married"]`，接触中不出现；日常问候 / 吃饭 / 周末这类暧昧向内容才含 `"talking"`。**`"lead"` 是「已相到人、还没赴约」专用的一档**（`CHAT_LEAD_PHASE`），只有 `phases` 里写了 `"lead"` 的对话才会在见面前被抽到。

新增婚嫁向内容时：事件加 `stage`（写进 `tools/gen-seed.js` 的 `EVENT_STAGE` 表），聊天把 `phases` 里的 `"talking"` 去掉。两边都不用改逻辑层。

| `ENCOUNTER_IMPROVE` | 0.10 | 提升自己 |

## 事件与聊天的结算规则

每个选项（事件选项与聊天回复共用一套）都对**全部属性**生效，且**有增有减**——没有白嫖的选项；奖惩幅度整体放大 2 倍。作者只写「意图值」：

```js
{ label: '直接买药过去', fx: { money: -80, affection: 13, mood: 4, health: -2 }, result: '……' }
```

生成时由 `tools/gen-seed.js` 的 `enrichFx(fx, 'id#选项序号')` 统一加工：

| 步骤 | 说明 |
| --- | --- |
| ① 放大 | 作者写的主影响 × `FX_AMP`（2.0） |
| ② 补覆盖 | 没写到的属性补一个较小的附带影响，直到覆盖 `FX_MIN_COVER`（5）项 |
| ③ 保取舍 | 保证至少 2 项为正、2 项为负，不够就把幅度最小的那项翻号 |

补齐值以 **`id + 选项序号` 为种子**确定性生成（`fxHash` / `fxRnd`，xorshift），**不是运行时随机**——同一个 id 每次生成结果完全一致，所以「结算不随机浮动」这条铁律没有被破坏。结算统一在 `engine.applyFx(s, fx)` 完成（事件与聊天都走它），渲染层拿到的 `delta` 就是真实发生的变化。

| 想改什么 | 改哪里 |
| --- | --- |
| 奖惩整体加倍 / 减半 | `FX_AMP` |
| 每个选项最少影响几项属性 | `FX_MIN_COVER` |
| 附带影响的最大幅度 | `FX_SIDE_MAX` |
| 扩充内容 | `tools/seed-more-events.js`（事件）/ `tools/seed-more-chats.js`（聊天），改完重跑 `node tools/gen-seed.js` + `node db/import.js` |

⚠️ `correct: true` 必须写在**选项层级**，写进 `fx` 对象里会被生成器忽略。

## 结局页 · 看广告领奖励（激励视频）

结局页底部两个入口**并行**，玩家自己选——广告不是继续游戏的强制门槛：

- **看广告 · +5000**（主按钮）：拉起微信激励视频，完整看完 → 奖励记下来 → 回标题开新一局
- **直接再开一局**：什么也不损失

奖励在**下一局开局时**一次性发放，**不改这一局结局页上已经展示的成绩**（那一局打出多少就是多少）；开局会用提示条告诉玩家「广告奖励到账：存款 +5000」。中途退出 / 广告没填充 / 广告位没配，都不发奖，并给出明确提示，玩家不会被卡在结局页。

配置全在云端 `constants`，改完 Upsert 导入即可，不用发版：

| 常量 | 作用 |
| --- | --- |
| `AD_ENABLED` | 总开关，设 `0` 后结局页只剩「直接再开一局」 |
| `AD_UNIT_ID` | **广告位 ID**：微信公众平台 → 流量主 → 广告位，创建后复制过来。默认占位值 `adunit-0000000000000000`，此时判定为「没配」，不显示广告入口 |
| `AD_REWARD_MONEY` | 看完一次给多少存款 |
| `AD_REWARD_MOOD` / `AD_REWARD_HEALTH` | 额外情绪 / 健康加成（填 `0` 就是不给） |

文案在 `texts` 的 `end` 文档：`againAd`（按钮，支持 `{money}`）、`adHint`（按钮上方那行说明）、`adLoading` / `adNotReady` / `adAbort` / `adRewardFlash`。

机制层在 `js/core/ad.js`：广告实例单例复用、`onClose` 先 `offClose` 再挂（避免一次展示回调多次）、`show()` 失败时补一次 `load` 再试、拿不到结果一律走降级。测试环境没有广告 API 会自动判 `unsupported`，所以 `ui-smoke` 那组断言用的是 mock 出来的假广告器。

> 真机跑之前记得：小程序后台要**开通流量主**并创建激励视频广告位，再把 ID 填进 `constants.AD_UNIT_ID`。开发者工具里可能拉不到广告，属正常。

## 关于平衡

`tools/smoke.js` 的模拟结果与参考项目**源码**行为一致。结束条件已按需求简化为三类：达成目标（胜）、任一核心属性归零（破产 / 病倒 / 失业 / 情绪崩溃）、以及相亲期限到期（仅限需要建立关系的目标；非相亲目标仍以 `maxDays` 为兜底）。已移除原「人生节点考核」（`GOAL_CHECK`，即「进度没到 x% 就停在原地」）与独立的「超期」判定。因此「独身千万 / 自由人生」等大额攒钱目标没有相亲期限压力，可一路攒到属性归零或达成目标。

相亲期限的计数规则（本轮调整）：

| 当前关系 | `singleStreak` | 说明 |
| --- | --- | --- |
| 单身且**手上没有对象**（`single` 且无 `lead`） | `+1` | 唯一真正走表的时段；到点仍未脱单 → 结局「在父母的催促下匆忙相亲结婚」 |
| 单身但**已相到人、还没赴约初遇**（`single` 且有 `lead`） | **不变（暂停）** | 当天刚相到人，给玩家从容安排见面的时间，不被倒计时逼死 |
| 初遇 / 接触中（meeting / talking） | **不变（暂停）** | 期限不会在接触中判负，保住剩余天数 |
| 恋爱 / 婚后（dating / married） | 归零 | 已确定关系，不再受期限压力 |

判定失败时还要求 **当前仍是单身**（`relationship === 'single'`），所以「期限到点但正在接触中」不会失败，可以继续把关系走完；分手或初遇失败清空对象后回到单身，会从暂停处继续走表。

倒计时卡片会按当前状态分别提示 `仍单身（正在走表）` / `已相到人，待赴约（倒计时暂停）` / `初遇中` / `接触中` / `已确定关系`——判断逻辑统一在 `engine.deadlineState(s)` 里，渲染层只负责展示，避免「卡片说暂停、实际却在扣天数」。

数值结算的随机浮动已按需求移除（原来是参考项目的 ±25%「肉鸽感」）。`tools/smoke.js` 300 局 × 多轮实测胜率：简单约 40–49%，普通约 20–25%，困难约 9–10%（设置页文案已同步为「普通难度通关率约 20%」）。困难档比上一版略高，是因为「手上有人时倒计时暂停」这条边界放宽了期限压力。注意每日自然衰减（`DAILY_HEALTH_DECAY` / `DAILY_LOOKS_DECAY` / `DAILY_AFFECTION_DECAY` / `DAILY_MOOD_RECOVER`）仍然保留 —— 那是「时间流逝」机制，所以隔天属性仍会有小幅变化，但**每次行动的结算数值本身是确定的**。
