# 《相亲模拟器》数据库设计文档

> 目标：把「玩法」与「数据」彻底解耦。引擎只描述规则，所有可配置内容（事件、角色、难度、数值、文案）都由数据库下发。

## 1. 集合清单（15 个）

| 集合 | 形状 | 内容 | 主键 `_id` |
|---|---|---|---|
| `events` | array | 116 条事件（单身 14 / 初遇 13 / 约会 22 / 接触 13 / 恋爱 12 / 婚后 7 / 通用 35），可带 `stage`（最低接触阶段）。其中 11 条是补充的相亲现场 + 单身期事件（`x_*`，真源在 `tools/gen-seed.js` 的 `EXTRA_EVENTS`） | 事件 id |
| `backgrounds` | array | 6 种出身背景（初始属性 + 职业 + 可选目标 + 头像 `avatar`） | 背景 id |
| `goals` | array | 6 种人生目标（声明式达成条件 + 进度） | 目标 id |
| `difficulties` | array | 3 档难度（11 个系数） | 难度 id |
| `channels` | array | 5 个相亲渠道（花费 + 成功率） | 渠道 id |
| `date_types` | array | 3 档约会（花费 + 好感倍率 + 时长） | 档位 id |
| `court_styles` | array | 6 种交往风格（好感增益 + 翻车风险） | 风格 id |
| `style_events` | array | 风格 → 匹配约会事件 id 列表 | 风格 id |
| `chats` | array | 36 个微信闲聊场景：23 条日常（`kind: normal`，含**见面前 `lead` 阶段 4 条**、父母催婚 / 个人慢热 / 现实因素）+ 6 条**灵魂拷问**（`grill`，按人格投放，踩雷大幅掉好感）+ 6 条**暧昧事件**（`flirt`，按人格投放，答对大幅涨好感）+ 1 条「必须出门约会」固定剧情（`mustdate`，不进随机池）。字段：`kind` / `personalityId` / `phases` / 开场白 `opener` / 候选回答 `options`（含 `correct`）/ 好感与情绪增量 | 场景 id |
| `partners` | array | 24 位相亲对象花名册（12 男 12 女）：姓名/性别/年龄/职业/头像 `avatar`/外形/性格/家庭/爱好/认识方式/人格/颜值/家境/眼缘 `first`/权重/一句话简介 | 对象 id（`p_f01`…） |
| `personalities` | array | 6 种对象性格（声明式主动分手条件） | 性格 id |
| `endings` | array | 13 种结局（6 胜 7 负）。字段：`type`（win/lose）、`art`（结局页页头画面类型：`happymarry` / `badmarry` / `alone`，渲染层据此拼 `assets/images/end/end_<art>_<性别>.jpg`）、`title`、`lines` | 结局 id |
| `constants` | object | 全部数值常量（衰减/成功率公式系数/时间成本/阶段顺序等） | `constants` |
| `materials` | object | 素材字典：职业（备注 + 头像 `avatar`）/性格（含好感系数 `mod`）/家庭条件（含金额系数）/外形/爱好/地点。对象文案与系数都按名字回查这里 | `materials` |
| `texts` | map | 17 份界面文案与旁白（`{_id, value}`），含 `gallery`（图鉴页） | 文案 key |

> 合计 249 条文档。`chats` 为「微信闲聊」二级页提供数据：`engine.pickChat(s)` 按当前关系阶段 + 好感门槛 + **对象人格**（`personalityId`）筛选后加权抽题，`engine.applyChat(s, opt)` **只改好感度与情绪**（好感度夹在 `0 ~ engine.affectionCap(s)`：单身 / 初遇 / 接触中上限 100，告白成功后放大到 500），其余指标不动。选项上的 `correct` 只用于展示与校验，不参与结算。

`texts.stat_defs` 除了决定每项属性的名称/颜色/上限，还带一个可选的 **`slot`（展示位）**字段：带 `slot` 的项不会出现在主界面的属性条网格里，而是挪到指定位置 —— 目前只有 `affection`（好感度）带 `slot: 'partnerHeader'`，即「挂在对象头像正下方（聊天框里有人就显示，含已相到人还未赴约的情况），数值显示成『当前 / 上限』」。

`stat_defs` 是**数组**，数组顺序就是主界面的排版顺序：渲染层一行放两条，所以默认顺序 `money, affection(slot), health, career, looks, family, mood` 去掉带 `slot` 的那一项后，恰好排成 **三行 × 每行两条**：存款/健康 · 事业/颜值 · 家境/情绪。好感度的 `max: 100` 只是单身期刻度，渲染时按 `engine.affectionCap(S)` 取当前上限（恋爱后自动变 500），所以进度条不会在恋爱后恒满格。换言之**属性条摆在哪里、按什么刻度画也是数据决定的**，渲染层只按 `slot` 与 `max` 分发。

## 2. 数据流

```
参考项目源码 (content.js/events.js/engine.js)
        │  tools/gen-seed.js 抽取
        ▼
db/seed/*.js（数据模板） ──db/import.js──▶ 云开发数据库
        │                                      │
        └──────────── js/db/repository.js ◀────┘
                              │ 归一化 + 缓存 + 完整性校验 + 同步读取
                              ▼
                    js/core/engine.js（纯逻辑）
                              ▼
                    js/ui/render.js（Canvas）
```

数据源：**微信云开发数据库（唯一）**。网络数据写入本地缓存，下次秒开；云端数据不完整 / 读取失败时，游戏显示错误页并列出问题清单。

## 3. 规则求值器（把函数改成数据）

源码里 `goal.check(s)`、`goal.progress(s)`、性格分手条件是函数，无法存数据库。本工程用声明式规则替代，由 `js/core/rules.js` 解释执行：

**条件节点**（`check` / `cond`）：

```json
{ "field": "money", "op": "gte", "value": 1000000 }      // 比较 s[field]
{ "flag": "child", "op": "eq", "value": true }           // 比较 s.flags[flag]
{ "all": [ ... ] }                                        // 且
{ "any": [ ... ] }                                        // 或
null                                                       // 恒真
```

**进度表达式**（`progress`）：

```json
{ "ratio": "money", "target": 1000000 }                   // min(field/target, 1)
{ "min": [ ... ] }                                        // 取最小
{ "mul": [ ... ] }                                        // 连乘
{ "cond": {...}, "then": 1, "else": 0.5 }                 // 条件三目
{ "type": "relation", "withChild": true }                 // 关系阶段进度
```

示例（「独身千万」目标）：

```json
{
  "id": "rich_alone",
  "check": { "all": [
    { "field": "money", "op": "gte", "value": 10000000 },
    { "field": "relationship", "op": "eq", "value": "single" }
  ]},
  "progress": { "mul": [
    { "ratio": "money", "target": 10000000 },
    { "cond": { "field": "relationship", "op": "eq", "value": "single" }, "then": 1, "else": 0.5 }
  ]}
}
```

性格分手条件（`personalities.rules`，`combine: "sum"` 时风险累加）：

```json
{ "id": "money", "combine": "sum",
  "rules": [
    { "cond": { "field": "money", "op": "lt", "value": 20000 },
      "risk": 0.06, "reason": "你账户里的数字，让她越来越不安。" }
  ] }
```

## 4. 接触阶段分级（暧昧 / 婚嫁）

同一份内容该在哪个关系阶段出现，用「接触阶段」描述，顺序取自 `constants.RELATION_ORDER`（默认 `single < meeting < talking < dating < married`）。判定在 `js/core/rules.js` 之外的 `engine.stageRank()` / `engine.stageOk()` 里做，**逻辑层只比较、不写死阶段名**。

| 集合 | 字段 | 语义 |
|---|---|---|
| `events` | `phase` | 内容属于哪一段关系（`single/meeting/talking/dating/married/any/date`），精确匹配当前 `relationship` |
| `events` | `stage`（可选） | **最低接触阶段**。不写 = 不限；写了就要求 `stageRank(relationship) >= stageRank(stage)` |
| `chats` | `phases` | 允许出现的阶段数组（显式列出）。除 `talking/dating/married` 外还有一档 **`lead`**（`constants.CHAT_LEAD_PHASE`）——「已相到人、还没赴约」专用 |

例：`dt_question_kid`（晚餐聊到「要不要孩子」）标 `stage: "dating"`，因此接触中不会抽到、告白成功后才会出现；`chats.c_mom`（见家长）的 `phases = ["dating","married"]`，同理。

**聊天阶段单独由 `engine.chatStage(s)` 给出**：有对象时就是关系阶段，只有「已相到人、还没赴约」时返回 `lead`。它不在 `RELATION_ORDER` 里，只是一个题库标签 —— 这样「见面前」的话题不会串到暧昧 / 恋爱阶段去。见面前对方也不会主动发消息（`rollProactiveChat` 直接返回 false），免得把「赴约」顶掉。

抽取路径都会过滤：`engine.pickEvent`（生活 / 提升 / 偶遇随机事件）、`engine.pickMeetingEvent`（初遇）、`engine.goDate`（约会档位事件）、`engine.chatPool`（微信闲聊）。

改动入口：事件的 `stage` 唯一真源在 `tools/gen-seed.js` 的 `EVENT_STAGE` 表；聊天的 `phases` 在 `CHAT_SCENARIOS` 里。改完重跑 `node tools/gen-seed.js` + `node db/import.js` 即可，引擎代码无需改动。

### 4.1 微信闲聊：调性、主动聊天与「必须出门约会」

`chats` 用 `kind` 区分四种调性，逻辑层只拿它做分支，**不写死任何文案或数值**：

| `kind` | 出现时机 | 设计意图 |
|---|---|---|
| `normal` | 随机池 | 日常闲聊，按 FX 规则对多项属性有增有减 |
| `grill` | 随机池 + 对象人格匹配 | **灵魂拷问**：问得刁钻，踩雷一次掉 20 点以上好感（要求至少 2 个选项 ≤ -20） |
| `flirt` | 随机池 + 对象人格匹配 | **暧昧事件**：答对一次涨 15 点以上好感，升温最快 |
| `mustdate` | **不进随机池**，全部条目都进固定剧情池 | 「必须出门约会」的固定剧情，凑够 `CHAT_MUST_DATE_AFTER` 次后按 `weight` 抽一条 |

**人格定向**：`chats.personalityId` 不为空时，只有「对象人格」（`partners.personalityId` → `personalities`）与之相等才可能抽到。因此每种人格都必须至少有一条 `grill` 和一条 `flirt`，同时**每种人格都要有相亲对象**，否则那部分内容永远见不到——这两点都由 `tools/smoke.js` 强制校验。

**主动聊天与「必须出门约会」**是一条状态链，全部存在存档里（`S.chatCount` / `S.proactiveChats` / `S.mustDate`）：

```
聊天记账（engine.afterChat）—— 见面之后（非 lead）的每一次微信都计入 S.chatCount：
  ├─ 玩家自己点开聊的 → S.chatCount += 1
  └─ 对方主动发来的   → S.chatCount += 1，并且 S.proactiveChats += 1

对方主动找你（每天开头判定一次，`lead` 阶段不触发）
  └─ Math.random() < constants.PARTNER_CHAT_RATE（默认 0.3）
       └─ openChat(proactive=true)：顶部标「对方主动发来了消息」，无「返回」
            └─ 聊完 → continueDay() 直接翻到下一天（跳过当天的行动选择）

S.chatCount >= constants.CHAT_MUST_DATE_AFTER（默认 2）
  └─ pickChat() 不再随机，直接返回 CHAT_MUST_DATE_ID 指向的固定剧情
       └─ 聊完 → S.mustDate = true
            ├─ rollProactiveChat() 返回 false（不再主动找你）
            └─ 聊天入口仍在，但点进去只显示 texts.chat.lockedLine
               （「我们还是多当面接触吧」）
            入口副标题实时提示进度：texts.chat.mustDateSoon（「…（2/2）· 下一次就该约见面了」）

玩家安排一次约会（engine.goDate）
  └─ S.mustDate = false、S.chatCount = 0、S.proactiveChats = 0（解锁 + 计数清零）
```

> **为什么用 `S.chatCount` 而不是 `S.proactiveChats`**：早期只用「对方主动发来的次数」计数，结果玩家如果每次都自己点开微信，计数永远是 0，这条规则就形同不存在（用户报过这个 bug）。现在改成**两种发起方式都算**，`S.proactiveChats` 只作为「对方主动」的明细保留。`lead`（还没赴约）阶段不计数，免得见面前就被逼出门。

阈值、概率、固定剧情的 `kind` 标记全部在 `constants` 里，换剧情只需改数据。

**结算口径**：聊天的每个回复与事件选项走同一套规则 —— `fx` 覆盖多项属性、且至少 2 正 2 负（生成时由 `tools/gen-seed.js` 的 `enrichFx` 按 `id#序号` 确定性补齐放大）。`options[].affection` / `mood` 只是给旧逻辑与旧云端数据兜底的扁平副本，数值与 `fx` 保持同一份。`correct: true` 写在**选项层级**，只用于展示与校验，不参与结算。

## 5. 相亲对象（`partners`）与相亲图鉴

### 5.1 对象不再是「随机拼装」

参考项目里对象是**每次现场拼装**的：姓名从姓名池随机、职业/条件按权重随机、颜值/家境再叠一层 `Math.random()`。
本工程改为**固定花名册**：`partners` 集合一人一条，姓名、性别、年龄、职业、**头像**、外形、性格、家庭、爱好、认识方式、人格、颜值、家境全部是登记好的数据。

```
engine.generatePartner(playerGender, playerLooks, playerFamily, metIds)
  ① 按玩家性别取异性花名册（DB.list('partners')）
  ② 优先排除本局已遇见的 id（metIds）→ 抽完才允许重复
  ③ 按 weight × 玩家条件（颜值/家境）加权抽一个人
  ④ engine.hydratePartner() 补齐运行时字段：
       职业备注 / 性格描述与好感系数 mod / 家庭描述 —— 按「名字」回查 materials
       人格名称与描述 —— 按 personalityId 回查 personalities
  ⑤ engine.markMet() 把 id 记进本局 s.met
```

- 逻辑层**不再**用 `Math.random()` 造姓名 / 职业 / 颜值 / 家境，这些字段全部来自数据库。
- 抽取本身仍是随机的（roguelike 需要），但抽的是「花名册里的谁」，不是「造一个新人」。
- 对象自带 `first`（眼缘）：见面时的初始好感偏移，替代原来的 `FIRST_RAND_*` 随机项 —— 同一个人每次见面结果一致，不同人之间有差异。

### 5.2 图鉴：收集进度存哪

图鉴把「有哪些人」（数据库）和「你见过谁」（本地存档）分开：

| 内容 | 存放位置 | 说明 |
|---|---|---|
| 对象资料（姓名 / 头像 / 职业 / 性格 / 家庭 / 颜值 / 家境 / 简介） | 云端 `partners` | 唯一真源，属于游戏数据 |
| 解锁与进展 | 本地 `xq_gallery_v1`（`js/ui/gallery.js`） | 玩家进度，**跨局累计**；存 `{ stage, aff, child, firstDay, lastDay }` |

- `stage` 取该对象达到过的**最高**接触阶段，顺序由 `constants.GALLERY_ORDER` 给出（默认 `met < meeting < talking < dating < married`）。
- 「待见面（lead）但还没赴约」记 `met`（已遇见）；赴约后按 `relationship` 递增，只升不降。
- 同步时机：每次 `saveGame()` 都会 `gallery.sync(S, S.day)`，因此每个行动结算完都会自动入账。
- 本局已遇见名单 `s.met` 随对局存进 `xq_save_v1`；图鉴记录独立存放，重开新局不会清空收集进度。

页面：主界面底部「相亲图鉴」/ 标题页「相亲图鉴」→ 分「女生 / 男生」两栏，一行三张卡片；已解锁显示头像 + 姓名 + 达成进展 + 好感度峰值，未解锁显示黑框 + `？` + 「未解锁」；点已解锁卡片进资料页。

## 6. 如何改数据（零代码）

| 想改什么 | 操作 |
|---|---|
| 加/改事件 | 改 `db/seed/events.js` 或直接改数据库 `events` 集合 |
| 调难度 | 改 `difficulties` 集合的 11 个系数 |
| 调数值公式系数 | 改 `constants` 集合 |
| 改文案 | 改 `texts` 集合（`envelope` / `recent` / `chat` 等文档） |
| 加/改微信闲聊 | 改 `chats` 集合（`opener` 开场白、`options[].affection/mood` 增量、`phases`/`minAffection`/`weight` 出现时机、`kind` 调性、`personalityId` 定向人格、`options[].correct` 标记） |
| 改主动聊天的概率 / 「必须约会」阈值 | `constants.PARTNER_CHAT_RATE`（默认 0.3）/ `CHAT_MUST_DATE_AFTER`（默认 2，按 `S.chatCount` 计数）；换成另一段剧情就改 `CHAT_MUST_DATE_ID` |
| 改「哪些结算页带头像与背景」 | `constants.RESULT_HEAD_ACTIONS`（默认 `confess,propose`）；场景兜底在 `assets/images/role-map.js` 的 `actionScene` |
| 改头像 | 改 `backgrounds.avatar`、`materials.jobs[].avatar`、`partners[].avatar`（填职业 key，如 `programmer`）；缺省回退 `role-map.js` |
| 加/改相亲对象 | 改 `partners` 集合（一人一条），或改 `tools/gen-seed.js` 的 `PARTNER_ROSTER` 后重跑生成 |
| 改暧昧 / 婚嫁的分级 | 事件加 `stage`、聊天改 `phases`（顺序常量 `RELATION_ORDER`） |
| 改图鉴阶段顺序 / 阶段名 | `constants.GALLERY_ORDER` / `texts.gallery.stages` |
| 新增目标/背景 | 在 `goals`/`backgrounds` 加记录（配合 `rules.js` 已支持的节点） |

改完重新导入数据库即可，引擎代码无需改动。

## 7. 存档

存档只存「id + 数值」，读档时用 `createGame` 重建 `goal/diff/bg` 引用（它们含规则数据，不序列化）。存档还带上 `history`（近期属性变化）、`acts`（近期经历日志）、`met`（本局遇见过的对象 id，避免重复抽到同一个人）、`chatCount` / `proactiveChats` / `mustDate`（微信一共聊过几次、其中对方主动几次、是否被要求「先当面见一面」）与 `today`（含事件页的 `resolved` / `chosenLabel`，保证「事件已确认、结果还在页内」的中断也能续上）。旧存档没有 `chatCount` 时按 `proactiveChats` 回填，不会崩。存档键：`xq_save_v1`。

相亲图鉴的收集进度单独存在 `xq_gallery_v1`（见 5.2），**跨局累计**，重开一局不清空。
